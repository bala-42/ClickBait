# ClickBait

> The only clickbait worth following.

ClickBait is a free, open-source (Apache 2.0), local-first AI companion that lives next to your cursor on macOS. Hold a hotkey, ask a question out loud, and it looks at your screen, answers by voice, and **points at exactly what to click**.

## Product principles
1. **Free and private by default.** Default path uses local models only. No account, no server, no telemetry. Screenshots never leave the machine.
2. **No paid keys, ever (decided 2026-10-10).** ClickBait must work fully for someone without any API key or paid account — most users, and the developer, don't have one. Local models answer; the optional internet features are free and keyless. The Anthropic provider was removed (roadmap D, done 2026-10-10); Ollama is the only provider.
3. **Point, don't just talk.** The overlay pointer is the core magic. Accuracy matters more than eloquence.
4. **Fast feels smart.** Target: spoken answer starts < 3s after the hotkey is released (measured: ~8 s for a screen question on qwen3.5:9b; instant pointing ~0.05 s). Stream everything.
5. **Portable core.** Keep logic that isn't macOS-specific in `ClickBaitCore` (no AppKit/SwiftUI imports) so a Windows shell can come later.

## Differentiators (earlier ideas; the master roadmap below takes precedence)
- **Guides: "show it once, it guides forever."** Record a workflow → saved as a portable JSON guide (steps + target element descriptions + AX identifiers, not video) → anyone can replay it with the pointer guiding them on their own screen. Guides re-locate targets on the live UI so they survive UI changes.
- **Autonomy slider.** Show me → Do it with me (ghost cursor, approve each click) → Do it for me.
- **Context-aware dictation.** Speak, it cleans up the text using what's on screen, inserts it into the focused field.
- ~~**Background agents** (BYOK only) via tool-use loop + MCP.~~ Dropped with BYOK (2026-10-10); revisit only with a free, local route.

## Tech stack
- Swift 5.10+, SwiftUI + AppKit, **macOS 14+, Apple Silicon**.
- Project generated with **XcodeGen** (`project.yml`). Never hand-edit `.xcodeproj`; regenerate it.
- Non-sandboxed app (needs Accessibility + Screen Recording). Hardened runtime on.
- Dependencies via Swift Package Manager:
  - `WhisperKit` (argmaxinc) for on-device speech-to-text.
  - Nothing else unless justified in the PR/commit message.
- Local LLM: **Ollama** HTTP API at `http://localhost:11434` (user installs Ollama and pulls a vision model). Model name configurable in Settings.
- No cloud model and no API keys (2026-10-10): the Anthropic provider was removed (roadmap D).
- TTS: `AVSpeechSynthesizer` (free, on-device). Speak sentence-by-sentence as text streams in.

### Ask flow (Milestone 1)
1. User **holds Control+Option** → start mic recording, capture screenshot of the display under the cursor, snapshot AX context (frontmost app name, window title, focused element role/title).
2. User **releases** → stop recording → transcribe with WhisperKit.
3. Downscale screenshot so the long edge is ≤ 1280px (keep the scale factor!) → send screenshot + transcript + context to Ollama (`OllamaProvider`).
4. Model must reply with JSON matching `AssistantResponse`:
   ```json
   {
     "speech": "Click the Share button in the top right.",
     "pointers": [{ "x": 1180, "y": 42, "label": "Share" }]
   }
   ```
   Coordinates are in the **downscaled screenshot's pixel space**. Parser must tolerate code fences / leading text and fall back to speech-only if JSON is invalid.
5. Map pointer coords → global screen points (account for downscale factor, Retina backing scale, display origin; AppKit's origin is bottom-left).
6. **Snap**: hit-test the AX element at that point; if a nearby actionable element (button, link, menu item, text field) within ~40pt better matches `label`, move the pointer to that element's center. Log original vs snapped.
7. Speak `speech`, animate pointer on the overlay, auto-dismiss after ~6s or on next click/Escape.

### Explain flow (added during M1)
Highlight text, then press and release **Option+Command** alone (no other key in between; `ChordDetector` in Core). The selected text is read via AX (`kAXSelectedTextAttribute`), sent with a screenshot for context, and the model returns a concise 2–4 sentence explanation in `speech` (usually no pointers). Same blocklist, provider and privacy rules as Ask. When Accessibility gives no selection, the fallback sends ⌘C (`SelectionReader`, clipboard restored) — but only once a possible second tap has passed (a double tap opens the chat and needs no selection), and never when the app's ⌘C menu item is disabled (`SelectionReader.copyIsEnabled`, read by its shortcut): a ⌘C with nothing highlighted made macOS play its alert sound on every ⌥⌘ double tap (2026-10-12).

### Commands (added after M1, step 10)
Direct orders spoken with ⌃⌥ are recognised from the transcript by `CommandParser` (Core) — plain rules, never the vision model (qwen2.5vl:7b missed real orders and acted on questions). Questions never act. Built-ins: open/quit app, volume, mute, Dark/Light Mode; plus Shortcuts the user ticked in Settings (the tick is the permission — they run without a prompt). Everything goes through `ActionCatalog.resolve` before `ActionExecutor` runs it. Unknown app names fall through to a normal answer.

### Models (2026-10-04)
- **One model by default: qwen3.5:9b** for everything — screen questions, pointing, snips, parts, plans, sorting, progress checks and order checks. A second model for order checks (qwen2.5vl:3b, ~0.15 s vs ~0.6–1.8 s) is optional in Settings ("Quick orders"), off by default: with both loaded (~10 GB) and Chrome, a VM and Xcode open, a 24 GB Mac had 14% memory free and was swapping, and both models ran at half speed (a 20 s answer; prompts read at ~200 tokens/s). With one model: 42% free, text prompts read at 400–630 tokens/s. If a second model is set and pushes the main one out, `OllamaProvider.fastModelEvictsMain` routes everything to the main model for the run.
- Models load at launch and stay loaded while ClickBait runs (`keep_alive: -1`); `unload()` frees them when it quits.
- Requests send `"think": false`: Qwen 3.5 otherwise thinks first (~10 s on a one-line answer; it once used the whole reply budget and returned nothing).
- Qwen 3 / 3.5 give positions as 0–1000 of the image whatever the prompt says (`CoordinateScale.thousandths`, chosen by model name); the element list is given in that scale (`PromptElement.line(for:)`, header without a unit) and `ResponseParser.parse(…, scale:)` converts back. Saying "0–1000" in the prompt made it refuse to point (19/39 vs 27/39).
- qwen3.5 can't reuse an unchanged prompt between requests (Ollama: "forcing full prompt re-processing … hybrid/recurrent memory"): every request reads its whole prompt. A screen question is ~2,800 tokens (instructions ~1,050, screenshot ~920, element list ~700) ≈ 8 s at ~350 tokens/s.
- Model replies to orders pass `OrderCheck.sanitized` (an app to open/quit must be named in the order; "this file" is never a new name).

### Instant answers (no model, 2026-10-04)
Only when there's no doubt; anything less takes the normal model path (user's rule: speed must never compromise functionality or robustness).
- **Pointing:** "where's / show me / point at / find the X" (`InstantAnswer.locateTarget`) with exactly one on-screen element named exactly X (`uniqueElement`; two of them in different places → the model decides) points at once (blue, ~0.1 s). The model still answers in words; its own pointers are ignored that time (`AskCoordinator.pointedInstantly`).
- **Menu walkthroughs:** a how-to or order whose task words (`taskPhrase`: openers, "my/the/this", the app's name stripped) equal exactly one menu item (`menuPlan`: "clear history" → History ▸ Clear History…) starts at once with open-the-menu + choose-the-item; what follows (a dialog's button) is planned by the model once the item is chosen.
- **"Show me …" always points (blue)** — the thing, or even "show me how to…" (`TutorialQuestion.asksToBeShown`; user's rule): never a lavender walkthrough, except a well-known website visit, which stays a typing step. "How do I… / walk me through… / orders" are walkthroughs.
- **Finding from the element list (text only):** a "where's / show me / point at / find X" whose X isn't named exactly is matched by a close name first (`closeElement`: every word of X in one element's name, "sidebar" → "Show Sidebar"), then by the model picking from the element list as text (`Prompt.pickSystem`, `pickElement`: ~1.5 s instead of ~9 s with the screenshot; 9/10 on a Safari toolbar test). The pick can return several elements (`{"ids": [...]}`, `pickedIDs`, at most 3): "show me where the back and forward buttons are" needs one per thing named, or it falls back to the screenshot (it used to pick only Back). "Show me / tell me where the X is/are (located)" and polite leads ("can you…") are recognised by `locateTargets`, so names on screen match instantly. **Content isn't picked from the list:** a request naming a date, day, month, number or event ("point to October 27th", "today's date", "my 3pm meeting", `InstantAnswer.namesContent`) skips the exact match and the pick and reads the screenshot. The list holds controls only, so in Calendar the pick landed on the nearest button ("Today" for Oct 27, "View" for today's date). Each pick must also fit what was named (`InstantAnswer.pick(_:fits:)`: a word of the target or a synonym — settings/preferences, back/previous, refresh/reload… — in the element's name), else the screenshot; the pick prompt says content is never in the list. The log names the target words and the picked element ("Pick for back + forward: \"Back\", \"Forward\"") so a wrong pick can be read off. Nothing fits → the screenshot as before. Finding questions skip the order check (~1.5 s). Unnamed text fields and areas are listed as "text box" ("where do I type?"). The pick runs for any locating question ("where do I type my message?", "which button sends it?" — `ImpliedPointer.isLocating`), not only "where's the X"; "show me how…" (possibly several pointers) still reads the screenshot. "… in Safari / on the toolbar / at the top" is where to look, not part of the name (dropped when something follows the preposition, so "Sign In" stays). An app named in a finding question that isn't in front ("show me the Share button in Safari") is opened or switched to first (green, `openForTutorial`), then ClickBait looks again and points (blue).
- An instant pointer answers without the model ("Here's New chat."): the model's sentence cost ~8 s of the GPU and the next question queued behind it.
- Pointing is always blue (`OverlayModel.tone`: guiding → idle), even while the words are still streaming.
- "Where are the back and forward buttons?" points at both when each is named exactly once (`locateTargets`; all or nothing). When the app in front has nothing on the cursor's display, the element list comes from the app whose window is under the cursor (`AXInspector.appPID(at:)`; its main window if it has no focused one) — instant pointing found 0 elements otherwise.
- An app menu named like its app ("Safari ▸ Clear History…") is a menu step, not an app to open (`separatingSetup` skips steps whose instruction says "menu").
- Element lists read the menu bar's titles before the window (a web page could use up the 0.4 s / 150-item budget, and the "Safari" menu wasn't found for 7 s).
- After the last planned step: if it was a dialog's button (AXButton) and that button is gone, the walkthrough finishes at once; otherwise the model is asked as before (a menu item usually opens a dialog).
- Guide motion: glide period 0.38 s, turn 0.3 s, label 0.22 s (was 0.6 / 0.45 / 0.3: "pointing must be immediate and quick"). A finished walkthrough shows a tick ("done" with ✓; "✓ Done!" in the chat).
- **Sorting how-tos (qwen3.5, ~0.8 s):** before planning, a request that isn't an instant website/menu walkthrough and doesn't ask outright ("show me how / walk me through / guide me / teach me / step by step": `insistsOnWalkthrough`) is sorted (`Prompt.sortSystem`, `sortRequest`): "answer" (about content — code, text, facts) skips the plan, which used to take 4–8 s and come back empty (one question took 20 s). Unsure or slower than 3 s → plan as before. The sort runs **alongside** the plan (both `async let`; a "question" verdict drops the plan), not before it, and is skipped for a how-to that names an installed app ("how do I open Safari history"). qwen3.5 sorted 23/24 and 15/16 unseen; qwen2.5vl:3b called every Mac task an answer (14/24, 16/24), so it isn't used.
- Models load at launch and stay loaded while ClickBait runs (`keep_alive: -1`, user's decision); `OllamaProvider.unload()` frees them when ClickBait quits.

### Pointing accuracy
Spoken and typed asks send the model a numbered list of up to 50 clickable things (question-word matches first, then open-menu items, then screen order) Accessibility reports on the captured display (`AXInspector.visibleElements`: open menus first, then the focused window, then menu bar titles; 0.4 s budget). The model may point by `"element": id`; when it gives x/y with a name that matches a listed element within 250 px, the parser uses that element's exact center. At ⌃⌥ press ClickBait sets `AXManualAccessibility` on the frontmost app so Chrome/Electron apps build their tree. Pointers no accessibility element confirms get a second look: a 1280×800 close-up (640×400 pt at 2× — qwen2.5vl's coordinates drift at other sizes) with the locate prompt; the triangle starts toward the rough spot and is retargeted when the close-up answers (~3–5 s). A new question cancels a running close-up. The close-up result is checked with Accessibility: a name match snaps onto the element; if Accessibility sees something else there (or the close-up finds nothing where Accessibility can see), the pointer is withdrawn ("I couldn't find that on screen"). Pointers are only kept for where/how/show/click/open questions.

### Listening
Recording continues 0.35 s after ⌃⌥ is released. `AudioConditioner` skips silent recordings (peak < 0.01), lifts quiet ones (up to 12×) and adds 0.2 s lead-in; Whisper's own no-speech filter is off. What was heard shows in a tiny pill while thinking.

### Places and file orders (phase E, steps 1–2)
- A box/circle snip in Finder selects the items under it (`AXInspector.finderItemNames` → `FinderSelection.select`; names reach AppleScript only via `AppleScriptText` escaping), so "combine these" acts on them.
- Rule-based orders (typed in a chat too): "make a new folder [in <place>] [called X]", "open Downloads", "move/copy these to <place>", "rename this to X", "put these in a new folder called X". Places: Desktop, Downloads, Documents, Applications, iCloud Drive; Home/Music/Pictures/Movies only with "folder". Names keep the user's casing and are validated (no `/`, `:`, leading `.`). Nothing is overwritten (numbered names); rename refuses clashes and keeps the extension.

### Built-in app orders (phase E, step 3)
"make a note: …" (Notes) — text keeps the user's casing, passed only as escaped AppleScript strings; "remind me to …" (Reminders, via EventKit) — title in small letters (web addresses excepted), always an all-day due date so it shows in the Today list: a day said in the order ("…tomorrow", "by Friday", "on the 12th", `ReminderText`) is used, else a green choice card asks "“…” — when?" (Today / Tomorrow, a 📅 button that opens a calendar in the card for any day up to a year ahead — the timeout becomes 60 s while it's open — or say/type any day, `ReminderDay.parse`; Esc or 20 s → not added); the pill names the list and day; "play/pause/next song/previous track" post the keyboard media keys (any player); "take a screenshot" (full: ScreenCaptureKit, without ClickBait or blocked apps; "area"/"window": macOS's own picker) saved to the Screenshot app's folder or the Desktop; "new Finder window"; "show desktop" (Mission Control). Timers/Focus need an allowed Shortcut.

### Orders in other words (phase E, step 4)
When the rules don't recognise something that looks like an order (not a question), a text-only request (`Prompt.orderSystem`, no screenshot, ~1.3 s on qwen2.5vl:7b, 8 s timeout) asks which catalog action it is, or none. The proposal must pass `ActionCatalog.resolve` and the Finder check. Safe actions run at once; `ActionCatalog.needsConfirmation` ones (trash, move, rename, move into folder, quit, shortcuts, Wi-Fi off, lock, sleep display) show a green confirm card (Do it / Cancel, "yes"/"cancel" by voice, Esc; 20 s timeout). Rule-recognised orders still run directly.

**IntentRouter — shadow mode (C3, 2026-10-20).** After each spoken question ends and ClickBait is idle for 1.5 s, a text-only request (`routeIntent`, `Prompt.routeSystem`, Ollama schema `{intent: answer|point|tutorial|order|clarify, app}`, 40 tokens, 3 s timeout) sorts the question; the reply is checked (`IntentRouter.parse`: known intent, app only if installed), retried once if bad, cached (200), and logged next to what ClickBait did: `Router (shadow): said tutorial (System Settings), ClickBait did answer: differs in 0.6 s`. It changes nothing and never runs while ClickBait is busy. Off: `defaults write org.clickbait.ClickBait router.shadow -bool false`. Next: read the log, then let it decide one intent at a time.

**Who asks first — `ActionPolicy` (user's rules, 2026-10-20).** Said clearly (`CommandParser`): the words are the approval; only binning files and quitting an app ask once. Guessed by the model: anything that changes something asks (open an app, note, reminder, volume, mute, Dark Mode, Wi-Fi, folder, every file action, shortcut, lock, sleep); only looking runs at once (screenshot, media keys, a place, a Finder window, the Desktop). Each asked action has its own question (`ActionCatalog.confirmationQuestion`). Replaces `ActionCatalog.needsConfirmation`.

### The chat belongs to where it was summoned
The chat stays on the desktop and with the app it was summoned in (`ChatController` home app). While another app is in front it steps away (hidden, nothing lost) and it's back where it was when that app is (`NSWorkspace.didActivateApplicationNotification`). Summoning it again elsewhere (double tap ⌥⌘) re-homes it there. An answer that arrives while it's away shows two pills where the user is: "answer's ready in Safari" riding with the companion (fades after 5 s), and below where it appeared a stay-put [let's see!] [later.] pill (fades after 10 s; Esc = later). "let's see!" clears both pills and brings that app forward, where the chat is waiting; going back there yourself clears both. The "answer's ready" pill stays its full 10 s even when the user clicks in other apps (`OverlayController.showReadyNote`; a click took it away at once, 2026-10-12, and the answer seemed lost). Walkthroughs take it along when they open or switch apps (`adopt`), since the checklist lives in it. Coming back, it shows 0.35 s after the app activates; a full-screen app's slide can take longer (it landed on Chrome's desktop and Claude's had none), so for ~1.5 s after, each finished desktop switch (`activeSpaceDidChangeNotification`) and checks at ~0.8 s and ~1.5 s move it to the desktop in view if it isn't there (`isOnActiveSpace`, logged).

### Pills before the chat
If a pill can say it, there's no chat. Pointing (blue pointer, labelled with the reply's own few words when they fit, `PillText`), an action's result (green), an error (black) and a short friendly answer (`PillText.fits`: one sentence, ≤32 characters — "Yep, it's on!") open no chat; the prompt asks for such replies when pointing or for simple facts. Longer answers, explanations, steps and code go to the chat; lavender walkthroughs always do. In a chat, such replies **park** it (`ChatController.park`: tucked, conversation kept; the "nothing in progress" safety net leaves it alone) until a long answer, a double tap ⌥⌘ or a new chat. A streaming answer brings the chat back only once it can't be a pill (a second sentence, or a first sentence past 32 characters). Near the right screen edge the chat's header flips (logo top-right) so the logo still sits on the companion. A double tap ⌥⌘ with text highlighted: the first tap's explanation may already have started its chat; it's only opened at commit and dropped on undo, so the double tap always gets a fresh (or the previous) chat.

### Chat tucks away while the answer comes
Sending a message (spoken or typed) tucks the chat panel into the companion (`ChatController.tuck`: shrinks, hidden, keeps its place; a first question opens tucked). Only the panel steps aside — pills, pointing and the orange spin carry on. When it appears (`untuck`) it pops out of the companion wherever the companion is at that moment, then stays there (`homePoint`); returning to its app shows it where it was as soon as the answer's first full sentence is in (`SentenceSplitter`), or at once for a reply, error, "Stopped", a tutorial checklist or the final answer; and whenever ClickBait goes idle with nothing in progress, so it can't stay hidden. If the text field had the keyboard, it gets it back.

### Type to ask (double-tap ⌥⌘, or ⌥⌘ + right-click)
Double-tapping ⌥⌘ (two taps within 0.3 s, `DoubleTapDetector`) opens the same chat without the mouse or a selection. A single tap still explains instantly (the request starts at once); for that 0.3 s it stays undoable: an open chat is detached but left on screen, and a "nothing highlighted" error waits. A second tap (or Esc) cancels the explanation quietly and puts the chat back (`undoExplain`); otherwise `commitExplain` closes the old chat. A snip or another shortcut resets the detector.
Right-clicking while holding ⌥⌘ opens an empty chat at the cursor with the text field focused (the panel takes the keyboard without activating ClickBait). The right-click (down and up) is taken by `InputInterceptor`'s event tap, so the app shows no context menu; the following ⌥⌘ release is ignored (not a tap/explain). The first typed message goes through `sendTyped` like any follow-up.

### Guided tutorials (lavender)
**"Go to / open YouTube" is an order (green), not a walkthrough**: a pure visit (`Websites.isJustAVisit`, not asked as a how-to) switches to a browser tab already showing the site (`AXInspector.selectTab`, by tab title) or opens its address in the named/default browser. "Show me how to open YouTube" and visits with more to do ("…and play lofi") stay walkthroughs. **Any request with "where" (anywhere in the sentence, `asksWhere`) is a blue point, never a walkthrough**, unless it also says "how". **"Where's / show me X" is showing where (blue), not how.** It becomes a walkthrough only when reaching X takes more than one click: X is an item inside this app's menus (`AXInspector.menuPath`, ≥2 levels), or a thing in another app the request names ("show me my Safari history"). A named control ("play button", "volume slider", `TutorialQuestion.namesControl`) or anything clickable on screen is always blue. Decided before any colour change, so a "where" never flashes lavender; walkthroughs from it skip the walkthrough-or-question sort. **Asked first.** Before a walkthrough points or opens another app, a lavender pill stays put by the companion with **[show me!] [✕]** — or **[show me in Safari!]** when it will switch apps (the warning is in the button). A request naming another app is offered before that app opens (no plan yet; a no gets a normal written answer); everything else is offered once its plan is ready (System Settings route, website, planned steps), and a no writes the plan's steps into the chat (`writeSteps`). ✕, Esc or 8 s without a click is a no (`offerWalkthrough` / `answerOffer`; anything that replaces the pill also answers no).
"How do I… / walk me through… / show me how…" (`TutorialQuestion`) is first planned (`Prompt.tutorialSystem`: screenshot + element list → `{"speech", "steps":[{"target","instruction"}]}`, structured output, ~6–9 s). Any plan whose first click is on screen or in the app's menus becomes a tutorial (even one step: the model often shortens plans); otherwise a normal answer. When the planned steps run out, the remaining steps are planned from where the user is (one call; "no steps" means finished; the companion stays put with "checking…") (≤2 continuations, ≤10 steps). Screen checks only move a tutorial forward. Plans stop at the finishing click; exact repeats are dropped. Planning (first and follow-up) is **text-only** when Accessibility describes the app (`TutorialPlanning.canUseTextOnly`: element list + menus, no screenshot): ~1–2 s instead of ~10–13 s with the same steps on qwen2.5vl:7b; the screenshot is used only as a fallback. The planner gets the app's real menus, trimmed to the question (`MenuOutline.relevant`; `AXInspector.menuOutline`, "History ▸ Clear History…") and a one-step "open the History menu and choose Clear History…" is expanded with the named item (`expandingMenus`). A follow-up plan that starts with an already-done step means the task is finished (`TutorialPlan.remaining`) — never walk it again. A screen sample is kept every second; if the next target doesn't appear within ~1.2 s of a step's click, the model is asked at once whether the task is done (a closing dialog usually means it is). A target that vanishes keeps the triangle at its last spot with the instruction as its label (element lists come back incomplete while menus are open; flying home and back looked jumpy). A menu item an earlier step already chose is never where a later step is (`TutorialPlan.choseEarlier`): Safari's dialog button "Clear History" vanished from one element list, matched the "Clear History…" item just used, and the walkthrough sent the user back into the menu to clear history twice (2026-10-06). Whenever the screen has changed since the last step and nothing happened for 5 s, the model is asked whether the task is done — completion never depends on seeing the planned click. During a tutorial (`TutorialController`) the companion is **Lavender (#B57EDC)**, points at each step's target with the instruction as its label, and the chat shows a checklist that ticks off. Watching, cheapest first: a click on the target (¼ s); the app's element list every ¾ s (target found by name via `StepMatcher`; a later step visible → jump ahead; a target inside a closed menu → `AXInspector.menuPath` and point at the menu to open first); a 128-px screen sample ~1/s only while the target can't be found; a model check (`Prompt.progressSystem`, ≥6 s apart) only when the screen changed and nothing else explains it. Screenshots stay in memory. Ends on the last step ("done!"), Esc, closing the chat, any new question, a blocklisted app, 90 s without progress or 5 min. A last step that is a menu item **without** "…" finishes at once (by macOS convention it acts immediately: "Show All History"); one with "…" opens a dialog, so the "anything left?" check still runs. The companion stays on a step until the user clicks: "went ahead" and the model's progress checks only move a step on after a click since it began (typing and shortcut steps advance when seen). It only points — never clicks for the user.
**System Settings tasks** (`TutorialQuestion.taskApp`: named, or a Mac setting — wallpaper, Bluetooth, Night Shift, "system setting(s)", "settings app"…) never plan from the app in front (that walked Finder's own "Settings…"): the walkthrough is the Apple menu → "System Settings…" (`TutorialPlan.systemSettingsByAppleMenu`, instant, pointed at, not opened for the user), then the rest is planned inside System Settings — unless getting there was the whole request (`onlyOpens`). A model plan with "Apple → System Settings…" is kept as pointing steps; the steps after it belong to System Settings. "Open System Settings" as an order still just opens it (green).
Known settings then go straight to their page and control (`SystemSettingsMap`, ~35 entries, page names checked against macOS 26/27's System Settings extensions): "night shift" → Displays → Night Shift. Facts, not model guesses (qwen3.5:9b sent Night Shift to General, then invented "Built-in Display → Touch"); anything not in the map is planned by the model once System Settings is open. A later step only counts as "gone ahead" in the app it belongs to, and after a step that opens an app ("System Settings…", `opensApp`) the tutorial waits up to 4 s for it instead of switching there itself.

**Orders and setup.** Orders that take clicks ("Clear search history.", "Refresh the page.") start tutorials too — not content requests ("write/summarise/explain…", `TutorialQuestion.isContentRequest`), which get normal answers, and not finding requests ("where's / show me / point at / find the refresh button", `isLocatingRequest`), which get blue pointing. Find = blue; do = lavender. If the task lives in another app — named in the request (`mentionedApp`, matched against installed apps) or planned as "Open Safari"/`"app"` (`separatingSetup`) — ClickBait opens it in **green** ("Opening Safari…"), waits until it's in front with readable menus (≤8 s), and plans there; apps and System Settings only, never websites (user's decision). It never does the task's own steps. When it finishes, a lavender card offers "back to <app>?" (Back / Stay; ignoring it = stay).

**Notes about what's on screen.** "Add this page's URL to my notes" / "note the selected text": a make_note or add_reminder whose text refers to the page (url, link, this page/site/tab) or the selection (`NoteReference`) gets that content instead of the order's words — the page's title and address from the browser's window (`AXDocument`) or web area (`AXURL`) via `AXInspector.pageAddress`, or the selected text. Nothing readable → an error, never a note of the order itself. "Add it / save that" (`.previous`) in a chat uses the last answer (`Conversation.lastAnswer`; just the link when it holds exactly one), else the selection; the user's own words are kept over the model's guess at "it". Notes get an HTML body (`NoteHTML`: one paragraph per line, the first is the title; links clickable). The id of the note made last is kept in memory (`ActionExecutor.lastNoteID`); "show me that note / open the note / open it" (`NoteReference.asksToSeeNote`) brings Notes forward with it (green "opening the note…").

**Websites and typing.** A step can be typing (`TutorialStep.typing`, the model's `"type"`, or read from an instruction like "Type youtube.com, then press Return" when the model leaves it out). Websites are typing steps in the user's browser's address bar (the planner is told the default browser): an address only for well-known sites the model is sure of, otherwise the site's name to search (user's decision, 2026-10-04). ClickBait never opens websites or types — the user types. Clicking into the field doesn't finish the step; the page changing to the typed site (`typedHost` vs `AXInspector.pageAddress`) does, or any new page for search text. Shortcut steps ("⌘C", `isShortcut`) show the instruction by the cursor and finish when the clipboard changes (copy/cut) or the screen changes ≥1.2 s after the step began — keys are never read. Targets written as menu paths ("Bookmarks ▸ Add Bookmark…") become open-the-menu + choose-the-item steps. A step whose instruction runs past 160 characters is the model reasoning inside the plan and is dropped. "I want to… / help me… / take me to…" ask for a walkthrough too (not "I want to know/understand…").

**An installed app beats a website of the same name:** "open Claude" / "go back to Claude" opens the Claude app (`Websites.visit(in:installedApps:)`); only "claude.ai", "the Claude website" or "Claude in Chrome" (`meansWebsite`) mean the site — it had opened the app, then switched to the browser to type claude.ai. "go back to / switch to / return to X" are open-app orders (`CommandParser`). **Well-known websites skip the model.** "open YouTube", "I want to watch YouTube", "take me to Gmail" (`Websites.visit`: a visit word plus a name from ClickBait's own list → address) become one typing step in the default browser's address bar, instantly — never a model-guessed domain. The browser is opened/switched to in green when it isn't in front. The address bar is found by shape (`AXInspector.addressBarFrame`: the widest text field near the top of the window, outside the page), not by a name. A plain visit (`Websites.isJustAVisit`) ends when the page opens; "watch lofi on YouTube" plans the rest from there. Plans log their steps ("Tutorial steps: …") and a first step that can't be found is named in the log. Plans send at most 25 menu items and 25 elements (qwen3.5 re-reads the whole prompt every time: Ollama logs "forcing full prompt re-processing … hybrid/recurrent memory"). Acting on an item (move, rename, compress) starts by selecting it; a sidebar place like Bin only opens it.

**Across apps.** Every step carries the app it happens in (`TutorialStep.app`; the model gives it per step, and "Open Notes"/"Switch to Notes" steps are dropped by `separatingSetup`, which assigns the following steps to that app; "ClickBait" is never an app, "System Preferences" → "System Settings"). When the next step's app isn't in front, the tutorial goes **green** mid-way ("switching to Notes…" / "opened Notes", once per step — a user who leaves again isn't fought), back to lavender, and re-plans that app's part from its real menus and elements (text-only, the earlier steps were guesses made in another app). Follow-up plans know the apps used and the app now in front. The chat checklist groups steps under "In Safari:" / "In Notes:" when a plan spans apps. A click on the menu the companion points at marks it open, and its item is then read straight from the menu bar (`AXInspector.openMenuItemFrame`) — the open-menu scan could miss it, so users had to click the menu several times.

### Parts tour (red, unlabelled images only)
A snip's answer may include `parts` (named parts of what was marked, positioned in the close-up's pixels; never written into the text). The close-up is sent at 1280 px on its long edge (`SnipView`), where qwen2.5vl:7b's positions are most accurate. Apple Vision text recognition reads the close-up's printed words on-device (`TextReader`, warmed at launch, waited for ≤1.5 s): if the part names are printed (`PartsMatcher` finds at least half of them), the image is **labelled and gets no tour**; plain text (a paragraph, code, a message: `PartsTour.isMostlyText`, long recognised lines or ≥200 characters in the marked area) gets no tour either — the names are already there. Otherwise the red companion always tours the parts (`PartsTour.stops`: 1–6 stops inside the marked area, each name once) with red pills reading "~ <name>": they're the model's best guesses (~46% land on the right structure, see below). ~2.4 s per stop, click to advance, Esc stops. The triangle's tip stops at the edge of the thing it names, not on top of it (user's request, 2026-10-06): `PartOutline` grows the region of similar colour (3×3 sample, RGB difference ≤ 60) around the part's point on a ≤320 px copy of the close-up and measures the edge in 16 directions; the overlay stops the tip where the approach direction meets it. A region over 20% of the marked area (a part of one larger drawing, or a point on the background) gives no outline, and the tip goes to the point as before. Apple Vision's object finders (foreground instances, objectness saliency) run on the whole close-up found only the big shapes in a solar-system test and missed every small planet; on small overlapping crops they find them all (below). **Parts are placed on things found on this Mac, not where the model says** (2026-10-06): qwen3.5:9b put the eight planets of a diagonal solar-system picture in an even row at y = 576, exactly 56 apart, nowhere near them. Now `ObjectFinder` (Vision foreground instance masks on overlapping 160/320/640 px crops of the marked area, started when the snip is made) finds the separate things (`ObjectMarks.merge`: one per thing, lines/specks/background dropped, ≤20, numbered left to right), draws numbered red badges beside them on the close-up, and the model says, mark by mark, which of the named parts each mark is on or "none" (`Prompt.marksSystem`, reply keyed by number `{"1": "Mercury", "2": "none"}`, enum-constrained; on a 960 px copy, ~6 s, after the answer is shown while the snip stays red). Asked name by name instead, it just counted 1, 2, 3… onto fish in the wallpaper when the box ran past the picture (1/9); a bare list lost track of which entry was which mark (9/15); folding the marks into the explanation request mixed up 4 of 8 planets. Keyed: 15/15 in order, 13/15 scrambled (Venus/Mars swapped — they look alike in that art), fish all "none"; 960 px reads in 2.4 s vs 4.0 s at 1280 with the same answers, 768 px fell to 7/15. The crops run concurrently (~1.1 s). Names given no mark are left out (the Sun, cut off at the edge, isn't found). No marks, or none named → the model's own guesses as before, unless they look laid out (`PartsTour.looksMadeUp`: ≥4 on one line, evenly spaced) → no tour rather than a wrong one. A tour's red pills centre their text, each line too (they were left-aligned: 9.5 pt left vs 12.5 pt right on one line, 9.5 vs 34–51 pt when a long name wrapped); blue and lavender labels stay left-aligned. Up-down too: a line box leaves room for capitals, so the (lowercase) names sat 1–2 pt low (9 pt above vs 5 below for "~ mercury"); `InkCentring` shifts one-line tour labels so the letters' ink is centred (SwiftUI's line is the font's height rounded up: 15 pt, not 14.1), now within 0.5 pt every way. "Where's X?" follow-ups in an unlabelled snip's chat point the same way. Nothing about parts is listed in the chat. If a first explanation names no parts at all, a background second look (`Prompt.partsSystem`, same close-up, the explanation as a hint, 20 s cap, cancelled by a new question/Esc) asks only for the parts and starts the tour when it answers.

### Parts tour: the standard (binding for all tour work, 2026-10-11)
Every red tour meets ONE standard for every picture a user circles (anatomy, connected diagrams, separate objects, line drawings, maps, machines, plants, photos):
1. Every part the explanation names that is really in the picture gets a stop; a name is left out only if the part truly isn't visible, and the log says why.
2. Each stop lands on the right part (the point on it, the tip at its edge): target ≥ 80% placed right on every benchmark image, ≥ 70% before anything ships; report per image.
3. Never a wrong tour: one blob never stands in for one part (`PartRegions.objectsAreUsable`), and positions that look made up (`PartsTour.looksMadeUp`) give no tour. An honest short tour beats a confident wrong one.
4. Labelled pictures and plain text get no tour — but a box mostly filled with a colourful picture (≥ 12% saturated, `PartsTour.pictureShare`) is never "text", caption or not.
5. The tour starts within ~3 s of the explanation finishing.
6. "~" labels stay until the benchmark shows a picture type meets 80% reliably.
**How parts are found** (`PartPlacer`, shared by asks and the benchmark; steps in `TourSteps`): separate things from Vision (`ObjectFinder`) are marks only if usable — at least half as many as the names (and 2), none covering > 40% of what was marked (A); otherwise the picture's measures (`PartRegions.measures`: colour variety, colourful share, stroke density) pick colour regions (C: region growing joined across outline strokes, background/specks/slivers/silhouettes dropped, badges ON each region), closed shapes of line drawings (D) or a numbered grid (E); the model names the marks once; names no mark took keep the model's own guesses ("~", unless `looksMadeUp`), faces snapping people. **Shipped: A.** C, D and E are built and tested but off: C scored worse on the brain diagram (below); D and E wait for the line-drawing, map, flowchart and photo pictures.
**Benchmark (run it before changing tours; never while the user is using ClickBait — ask first):** boxes in `docs/tour-benchmark/boxes.json` (paths and boxes only; the pictures stay outside git). `CLICKBAIT_TOUR_BENCH=docs/tour-benchmark/boxes.json CLICKBAIT_TOUR_BENCH_OUT=<folder> CLICKBAIT_TOUR_STEPS=A CLICKBAIT_TOUR_RUNS=2 [CLICKBAIT_TOUR_ONLY=<name>] build/DerivedData/Build/Products/Debug/ClickBait.app/Contents/MacOS/ClickBait` — each picture as a whole-picture snip through the real path; a stop is right inside one of its part's boxes (4% of the longer side as slack, `exclude` boxes don't count), names matched loosely (`TourScore`); writes `report-<steps>.md` and renders (marks, stops, boxes). Latest (2026-10-11, 2 runs each): brain section — today 4/6 (67%), first stop 3.8–4.8 s; A 5/6 (83%), 1.4–1.5 s; AC 2/6 (33%), 3.8–6.8 s (the model named only 3 parts: cerebrum, cerebellum, brainstem). Solar system (boxes still to be confirmed by the user) — today 9/10 (90%, the Sun dropped), A 11/12 (92%, the Sun toured), 4.0–4.2 s. Anatomy diagram not yet run.

### Background ClickBaits (the agent dock)

### Snips (phase C)
Hold ⌥⌘ for 0.4 s to arm (companion turns red, trackpad tick); only then a transparent layer covers every screen (below the companion, which turns Strawberry Red). Moving traces a red line; click-drag draws a box (the click never reaches the app). Release decides (`SnipTracker`): a box ≥ 12 pt or a trace ≥ 60 pt long is a snip, anything else is a tap → explain highlighted text. The screenshot is cropped around the region (`SnipLayout`) with the shape drawn in red (`SnipRenderer`), sent with `AskRequest.snip`, answered in a chat bubble like an explanation (no pointers, no speech). Failsafe: the layer cancels itself if ⌥⌘ is no longer held or after 60 s. Trade-off: ⌥⌘-click/drag in other apps (e.g. Finder alias drag) is captured while the chord is held.

### Overlay rules
- `NSPanel`, borderless, non-activating, `isOpaque = false`, clear background, `ignoresMouseEvents = true`, level `.screenSaver`, `collectionBehavior` includes `.canJoinAllSpaces`, `.fullScreenAuxiliary`, `.stationary`.
- **Flights (2026-10-11, after Clicky):** guided moves and the trip home fly `FlightArc` (Core): quadratic Bézier, control point the midpoint raised min(d·0.2, 80) pt, smoothstep, clamp(d/800, 0.6, 1.4) s, swell 1 + 0.3·sin(πp), glow +(scale−1)·20 pt (a pre-drawn radius-14 glow faded in, not re-blurred). Short hops: no arc/swell below 120 pt, full from 400 pt, linear between. Faces its travel heading until 70% (`turnInAt`), then the turn spring aims it; it lands exactly where the glide did. Home flight cancels if the mouse moves > 100 pt. Reduce Motion: jumps / glides as before. Turn and swell reach the view only in 0.25° / 0.01 steps, through a small `LiveCompanionTriangle` that alone reads them. Benchmark tour main thread 0.55–0.66 → 0.79–0.81 s, 0 stalls. Measured why (2026-10-11): heading off 0.81 s, swell off 0.77 s, both off 0.57 s — any SwiftUI change to the triangle during flights costs ~0.2 s per tour, nearly independent of how often (60 Hz cap: 0.72–0.74 s, dropped as not worth losing 120 Hz). The remaining fix would be turning/scaling the triangle with Core Animation outside SwiftUI (not done: its rotation sign can't be checked by screenshot, the overlay has `sharingType = .none`).
- **Guide labels pop in (2026-10-11, after Clicky):** each label (`GuidePill`, one view kept across stops, reset on `onChange(of: label)` in the same update as the new words) pops from scale 0.5 to 1 with `.spring(response: 0.4, dampingFraction: 0.6)`, its glow starting bright (+1.0 opacity, +16 pt at half size) and settling — a glow drawn once behind the pill and faded out, since animating the shadow's radius re-blurred it every frame (+0.12 s a tour, a 91 ms stall). Benchmark: tour 0.74–0.84 s, point 0.17–0.21 s, spin 0.35–0.37 s, 0 stalls in 4 runs.

- Pointing (phase B): no separate arrow. The triangle detaches, glides to each target and turns its vertex onto it, with a label pill on the side away from the target ("1/2 · File"). Arrived = the flight is over (or none, Reduce Motion), the triangle is at its final spot and has finished turning onto the target (`GuideTiming.hasArrived`); a new or corrected flight resets it; the pulse (`isGuideSettled`) also starts then. Logged: "Guide: arrived at target N after X s". Safety cap 12 s from setting off (`GuideTiming.maxStop`). Until 2026-10-11 both the blue hold (1 s) and the tour hold (2.4 s) were timed from the first frame, before the flight had moved, so a blue point left ~1 s after setting off. A new question or closing the chat sends it back. Esc stops whatever ClickBait is doing (listening, thinking, speaking, snip, pending confirmation, close-up, pointing); with nothing going on it closes the chat. Reduce Motion: it jumps instead of gliding.

### Esc (user's rule, 2026-10-11)
**Esc while ClickBait is working, thinking or listening only puts ClickBait back to idle blue — it never reaches, closes or stops anything else on the Mac.** `InputInterceptor` (an event tap) takes Esc, its repeats and its key-up whenever ClickBait owns it: `AskCoordinator.ownsEscape` (`isBusy`, plus a walkthrough offer waiting, an explanation still undoable, an app opening for a walkthrough) or `OverlayController.looksBusy` (listening/thinking/working words, spinning, pulsing, red over a snip, pointing, touring) or a card/ready pill of ClickBait's own. A taken Esc runs `overlay.onEscape`: `stopActivity()`, a card still up answers "no" (`ConfirmController.cancel`, so its asker hears back), then `resetToIdle()` (no guide, no red, no words, companion shown). It never closes the chat and never stops a background job. Idle, Esc passes through untouched (logged "Esc passed to the front app"). A watchdog re-enables the tap every 3 s if macOS switched it off. Check (no model): `open --env CLICKBAIT_BENCH=esc …/ClickBait.app` posts a real Esc while idle (must pass) and while spinning (must be taken, then "bubble idle, spinning false").

**Guidance (2026-10-17)** — `GuidanceController` (app) + `Guidance` (Core). No paid services or API keys (2026-10-10); no cloud model.
- **Internet Mode (built 2026-10-10):** an opt-in 🌐 switch in the menu bar, off at every launch, never saved, never switched on by ClickBait. The local model writes every answer; no paid services, no keys, no ClickBait server. Only search words and page addresses go out — to Wikipedia, Stack Overflow (Stack Exchange API), MDN, Apple developer documentation, the pages read, and SearXNG on this Mac if it runs — never the screenshot, the screen's text, audio, chats, element lists, or a name found on screen. A search phrase about the screen is written by the local model from on-screen words and cleaned first (≤12 words / 100 characters; email and web addresses, paths, long numbers and key-like strings removed; names found on screen removed unless the user said them). Only when the user's words ask (`WebLookup.reason`); the one exception is a snip while 🌐 is on (its subject → Wikipedia; nothing sent for a face or text). An address is read only if it appeared in the user's words, on screen or in a result (HTTPS; HTTP only for localhost). Web text only informs a written answer — never an order, walkthrough or file action. Recent searches: last 5, memory only. Design: `docs/superpowers/specs/2026-10-07-internet-mode-design.md`.

- No web lookups for answers or ⌥⌘ explanations otherwise (decided 2026-10-01): they use only the screen and the model's own knowledge. The exception is Internet Mode, above, when the user switches it on.
- Never write screenshots or audio to disk except to a temp dir that is deleted after the request (debug mode may keep them, off by default).

### Parts tour: measurements (2026-10-04)
Why the tour is unlabelled-only and says "~" (built fbee451, removed f2b173c, brought back as best guesses):
- Labelled diagrams: placing parts by their printed labels (Apple Vision text recognition) was accurate, but a tour of names already on screen is useless.
- Unlabelled images (where a tour would teach something): scored on five real images (shoulder anatomy, a circuit, the visual pathway, an Ohm's-law worksheet, the solar system), one "find X" locate per part, a part counted right if its point fell on the right structure:
  - qwen2.5vl:7b: 18/39 (46%), ~3 s per part. One-call variant: mis-recognised the shoulder as the ear.
  - gemma3:12b: 7/39 (18%), ~5–6 s per part; it answers the image centre when unsure (no pixel grounding).
  - qwen3.5:9b (positions read as 0–1000): 27/39 and 25/39 on two runs (~66%), ~8 s per part (with `think: false`); read as pixels only 14/39. Telling it "0–1000" in the prompt: 19/39 (it returned no pointer more often).
