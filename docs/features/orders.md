# Orders

Places and file orders, built-in app orders, orders in other words, and who asks first (`ActionPolicy`). Part of the project rules (see `CLAUDE.md`).

#### Places and file orders (phase E, steps 1–2)
- A box/circle snip in Finder selects the items under it (`AXInspector.finderItemNames` → `FinderSelection.select`; names reach AppleScript only via `AppleScriptText` escaping), so "combine these" acts on them.
- Rule-based orders (typed in a chat too): "make a new folder [in <place>] [called X]", "open Downloads", "move/copy these to <place>", "rename this to X", "put these in a new folder called X". Places: Desktop, Downloads, Documents, Applications, iCloud Drive; Home/Music/Pictures/Movies only with "folder". Names keep the user's casing and are validated (no `/`, `:`, leading `.`). Nothing is overwritten (numbered names); rename refuses clashes and keeps the extension.

#### Built-in app orders (phase E, step 3)
"make a note: …" (Notes) — text keeps the user's casing, passed only as escaped AppleScript strings; "remind me to …" (Reminders, via EventKit) — title in small letters (web addresses excepted), always an all-day due date so it shows in the Today list: a day said in the order ("…tomorrow", "by Friday", "on the 12th", `ReminderText`) is used, else a green choice card asks "“…” — when?" (Today / Tomorrow, a 📅 button that opens a calendar in the card for any day up to a year ahead — the timeout becomes 60 s while it's open — or say/type any day, `ReminderDay.parse`; Esc or 20 s → not added); the pill names the list and day; "play/pause/next song/previous track" post the keyboard media keys (any player); "take a screenshot" (full: ScreenCaptureKit, without ClickBait or blocked apps; "area"/"window": macOS's own picker) saved to the Screenshot app's folder or the Desktop; "new Finder window"; "show desktop" (Mission Control). Timers/Focus need an allowed Shortcut.

#### Orders in other words (phase E, step 4)
When the rules don't recognise something that looks like an order (not a question), a text-only request (`Prompt.orderSystem`, no screenshot, ~1.3 s on qwen2.5vl:7b, 8 s timeout) asks which catalog action it is, or none. The proposal must pass `ActionCatalog.resolve` and the Finder check. Safe actions run at once; `ActionCatalog.needsConfirmation` ones (trash, move, rename, move into folder, quit, shortcuts, Wi-Fi off, lock, sleep display) show a green confirm card (Do it / Cancel, "yes"/"cancel" by voice, Esc; 20 s timeout). Rule-recognised orders still run directly.

**Who asks first — `ActionPolicy` (user's rules, 2026-10-20).** Said clearly (`CommandParser`): the words are the approval; only binning files and quitting an app ask once. Guessed by the model: anything that changes something asks (open an app, note, reminder, volume, mute, Dark Mode, Wi-Fi, folder, every file action, shortcut, lock, sleep); only looking runs at once (screenshot, media keys, a place, a Finder window, the Desktop). Each asked action has its own question (`ActionCatalog.confirmationQuestion`). Replaces `ActionCatalog.needsConfirmation`.

**Shrinking videos (2026-11-01, user: "it can not shrink my videos").** Videos went through Apple's HEVC 1080p export preset, which picks its own bitrate — higher than an already efficient video's (the user's 15-minute 1080p H.264 at 3.3 Mbit/s) — so the copy came out no smaller and was discarded as "already as small as I can make it". Now `shrinkVideo` re-encodes with AVAssetReader/Writer: HEVC at about half the original's bitrate (at least 0.8 Mbit/s), at most 1080p on the short side (shape kept), AAC audio at 128 kbit/s. Measured (`ShrinkVideoTests`, opt-in, copies of two of the user's shampoo videos): 2.26 GB → 1.14 GB in 194 s.

**Converting videos, and files from anywhere (2026-11-01, user: "change the video to different formats like mp4", and "why only from finder? … my file shelf").** `convert_videos` (`FileAction.convertVideos(to: MediaFormat)`): "convert this video to mp4", "save this as a mov", "turn this video into a gif", "extract the audio" / "to mp3" (→ M4A: AVFoundation can't write MP3). MP4, MOV and M4V repackage the streams as they are (passthrough: instant, no loss) when the container takes them, else re-encode at the highest quality; M4A is the sound alone; a GIF is up to 150 frames across the video (≤ 10 a second), 480 px, looping. Measured on a copy of a 2.4 MB clip: MP4/MOV/M4V instant and playable, M4A 303 KB, GIF 4.4 MB in 3 s (`ConvertVideoTests`, opt-in).
Actions that only make new files (`FileAction.makesCopies`: shrink, convert, zip, combine) now take, in order, the files selected on the notch's shelf (and put what they make back on the shelf), the document open in the app in front (its `AXDocument`: QuickTime's video, Preview's PDF), then Finder's selection. Trash, move and rename stay Finder-only: "delete this" in a text editor must never touch files.

**Convert anything (2026-11-02, user: "convert mov to mp4 … allow for images, files … pdf, doc").** One `convert` order (`FileAction.convert(to: FileFormat)`; the old convert_images/convert_videos names still resolve), its target the last format named ("convert this mov to mp4" → MP4; "word" → .docx, "mp3"/"audio" → M4A). By file: videos → MP4/MOV/M4V (passthrough, else re-encoded), M4A, GIF; images → JPEG, PNG, HEIC, TIFF, GIF, BMP, PDF; PDFs → text, Word, RTF, web page, OpenDocument (their text), or images (one per page, 2×); documents (.docx, .doc, RTF, text, Markdown, HTML, OpenDocument, web archive) → PDF (Core Text on A4, 2 cm margins), Word, RTF, text, web page, OpenDocument. Files a format doesn't fit are skipped and named. "Word" alone isn't a file reference ("delete the last word" is about text). Measured end to end (`ConvertAllTests`, opt-in): all of the above, the user's 146 MB clip MOV → MP4 instantly.
**The failed "mov to mp4" (user's report):** the file was a shrink cut off part-way (the app relaunched mid-encode) — no index ("moov atom not found"), unreadable by anything. Now a shrink writes to a temporary file and moves it in only when complete; a damaged video is named as such ("damaged or unfinished … cut off while being made"); and exports are tried rather than trusting `compatibleFileTypes`, which said no to videos it could export.

**Shrinking to a size (2026-11-02, user: "it is not respecting the file size i request").** Shrink took no size: it always aimed at about half (2.59 GB → 1.3 GB). Now `FileAction.shrink(toBytes:)`: a size said anywhere in the order ("shrink this to 200 MB", "under 5 megs", "1.5gb", "500 kb"; `FileSize`, decimal units as Finder shows) is the target, from the parser or the model's guess (`OrderCheck.sanitized` takes it from the words said); "compress this to 200mb" is a shrink, not a zip. Each copy aims under it: videos at the bitrate the length allows (6% spare), the picture made smaller as the bitrate falls (1080/720/480/360 on the short side), audio 128 or 64 kbit/s, and a second, lower try if the encoder overshot; a target too small to watch is refused with the smallest sensible size. Images step down quality, then sides, until they fit. PDFs get the system filter only; one that can't reach the target says so ("that's as small as I can make it"). Files already under it are left alone. Measured on copies (`ShrinkTargetTests`, opt-in): a 149.6 MB clip → 38.7 MB for 40 MB in 34 s; a 233.7 MB JPEG → 184 KB for 200 KB; a 3.7 MB PNG → 283 KB for 300 KB.

**"50 mb" still failing (2026-11-02, user's report).** Two bugs. (1) The size was lost between the parser and the catalog: the parser wrote bytes ("50000000"), `ActionCatalog.resolve` read the argument as words and found no unit, so the target was nil (388 MB → 202.8 MB). It now takes bytes or words; a test runs said → parsed → resolved. (2) A file job sent to the dock left ClickBait "thinking", so it stayed busy (hotkeys ignored) until Esc; `startFileJob` now frees it (speaking, or idle). Also: sizes said in words ("fifty megabytes", "two hundred and fifty mb", "a hundred megs"; `FileSize.digits`), the tile names the target ("Making smaller copies under 50 MB…"), folders count as "can't shrink" rather than "already under", and `File action on N from Finder/the shelf/the document in front: sizes` is logged. Verified live: "shrink this to 50 mb" on a copy of a 388 MB 1080p MP4 → 48.4 MB in 26 s (360p at 352 kbit/s: it's long).

**Every file order asks first (2026-11-02, user: "there should be a confirmation pill before the work of file manipulation begins").** `ActionPolicy`: any `.file` order asks, said clearly or guessed (was only trash and quit); the question counts the files from where they'll come (the shelf, the document in front, else Finder). "Yes" then sends copy-making jobs to the dock. Debug `org.clickbait.debug.order` goes through the same ask-first route. Checked live: "convert this to a gif" with a clip selected → "asking first", nothing made.

**Pills in small letters, names kept (2026-11-02, user: "the messages in pills should be in all small letters except the names of the important stuff").** Every pill now goes through `PillCase.lowered` with the installed apps' names: the companion's pills (answers too, which used a flat `lowercased()` and turned "Safari" into "safari"), working pills, and now the confirmation and choice pills (question, buttons, hint, options: "convert 1 item to MP4?", "do it", "cancel"). Names that keep their capitals even first in a sentence: apps, places, ClickBait's own features (Studio, Lookup, Shelf, Vision Memory), days and months; abbreviations (MP4, PDF, MB) and inner capitals (AirDrop, iCloud) always. Chat answers and Settings stay in normal sentence case.

**Archives (2026-11-02, after MacPacker's Finder menu).** Three orders, on macOS's own tools (`/usr/bin/tar`, libarchive: zip, tar, gz, bz2, xz, 7z, iso, cpio, xar…, and `/usr/bin/zip`), no new library:
- **peek** — "what's in this zip?", "peek inside it", "look inside this archive": how many files, their total size and the first few top-level names ("t.zip: 2 files, 2 KB: a.txt, photos/"). Read-only: runs without asking, from the shelf, the document in front or Finder (`FileAction.worksBeyondFinder`). `ArchiveListing` reads `tar -tvf` (names with spaces, folders, Finder's `__MACOSX`/`.DS_Store` left out).
- **extract** — "unzip this", "extract it into Downloads", "open this zip": each archive into a new folder named after it ("t.zip" → "t", then "t 2"; "x.tar.gz" → "x"), next to it or in the place said; never loose files. A password-locked archive says so ("…is password-locked; I can't open it without the password") and leaves nothing behind. tar would ask for the password on the terminal and wait forever (a test hung on it), so it gets a stand-in and fails at once. "extract the audio" still converts.
- **zip styles** — "zip each of these separately" (one zip per item), "zip it with today's date" ("a.txt 2026-11-02.zip"), plus the old one-zip-of-everything.
Extract and zips ask first and run as Shamrock dock jobs like the other copy-making orders. Tests: `ArchiveActionsTests` (peek, extract twice, each, dated, a locked zip), `ArchiveListingTests`. Not done: 7z output (needs a library), adding to an existing zip.

**"peek at it?" (2026-11-02, user's idea).** An archive dropped on the shelf gets an offer by the companion, 1.4 s after "added … ✓": "peek at it?" in the idle look, [peek] / [not now], "or say “peek”", gone after 8 s, never twice for one file (`offeredPeeks`). It's a pending action aimed at that file (`pendingAction.files`, `AskCoordinator.offerPeek`), so a click, "peek", "take a peek", "look inside" or "yes" all take it, by voice or typed. Taken, it runs green (the working pill) and its result comes back through `onOfferResult` for click and voice alike (`perform(quiet:)` skips the plain done pill): the contents in a green card with [extract] / [done]; extract goes straight to the dock (the card was the asking). Debug: `org.clickbait.debug.peekoffer <path>` makes the offer, `org.clickbait.debug.answer yes|no` answers it. Checked live: offer → yes → "File action on 1 from the shelf" → peek done.

**Claude Code and Codex notices (2026-11-02, user: "a notification … that the claude code or the codex needs an action from the user or … that task has completed"; "ok to add hooks").** A pill by the cursor (the user's rule for notices), skipped while the app the agent runs in is in front:
- **Claude Code** — through its own hooks. With the setting on, ClickBait adds two to `~/.claude/settings.json` (Notification: it needs your permission or input; Stop: it finished), beside the user's own (`AgentHooks.adding/removing`: never twice, the user's groups untouched, the file backed up once as `settings.json.before-clickbait`, never written when it isn't readable JSON). Each runs `/bin/sh '<ClickBait.app>/Contents/Resources/clickbait-agent-event.sh' claude`, which appends one line — the tool, the app it runs in (`__CFBundleIdentifier`: Terminal, iTerm, VS Code, the Claude app) and Claude Code's hook JSON — to `~/Library/Application Support/ClickBait/agent-events.jsonl`. "Needs you" is a card with [go there] (brings that app forward), its message as the hint, with the needs-you sound; "finished ✓" a pill with the done sound.
- **Codex** — finished only, from its session logs (`~/.codex/sessions/YYYY/MM/DD/*.jsonl`, `task_complete`), since its one `notify` setting already belongs to OpenAI's Computer Use helper on this Mac, and its logs record no approval requests (none in 15 sessions).
`AgentWatcher` checks once a second (two file sizes, today's and yesterday's Codex folders), reading only what's new since ClickBait started; the events file is emptied past 256 KB. Asked once on launch (`agentNoticesAsked`); "Claude Code and Codex notices" in Settings adds or removes the hooks; Uninstall removes them. Checked live: hooks added beside the 10 existing hook events with all settings kept; a simulated Stop from Terminal → "Claude Code finished ✓ · landing". Tests: `AgentNoticeTests`.
