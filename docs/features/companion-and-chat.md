# The companion and the chat

Companion motion, the greeting on coming back, where the chat opens, pills before the chat, typing to ask, and chat bubbles. Part of the project rules (see `CLAUDE.md`).

#### Companion motion
Listening: the waveform, Clicky's (MIT, 2026-10-11): five 2 pt bars 2 pt apart (corner 1.5), profile 0.4/0.7/1/0.7/0.4, height 3 + 10·eased level·profile + a 0–1.5 pt idle pulse (sin(3.6·t + 0.35·i)), glow 0.6 / 6 pt, `TimelineView` at ≤ 36 fps, in the state's colour; level = loudness on a −45…−15 dB scale, rising at once and falling ×0.72 per 1024-sample buffer as Clicky's, converted to frame time (`WaveformMeter`, Core). Not Clicky's RMS ×10.2: measured on this Mac (speech from the speakers, RMS median 0.025, 90th percentile 0.068, room 0.007) it pinned the middle bar at the top from RMS 0.035, so a close voice wouldn't move it; on the dB scale room ≈ 1.3 pt, median speech ≈ 5.3, loud ≈ 7.8, close ≈ 9.6 of 10. Each listen logs "Waveform: loudest RMS … → level …". Was 3.5 pt capsules on a dB scale. Reduce Motion: no idle pulse. **Thinking (Pumpkin #FF7518, `isSpinning`): the triangle turns a third at a time** — each tick (0.5 s) springs ~20° past and settles (an underdamped step), then rests 0.4 s; a triangle looks the same every 120°, so ticks end where they began. When thinking stops mid-tick it springs to the nearest third. Working (green), snipping (red, while marking) and pointing (blue or lavender, once arrived) pulse; a red parts tour never pulses — it holds steady on each part (user's rule, 2026-10-11; `OverlayModel.isPulsing` excludes `isTouring`). Benchmark tour phase: main thread 1.17–1.21 → 0.55–0.66 s (no per-frame glow redraw), spin 0.34–0.39 s, point 0.18–0.19 s, 0 stalls. A snip stays red and spinning from the circling until its parts tour starts (`isSnipThinking`, ended by the coordinator when the tour starts or there's nothing to point at; also by an error or a new question). Parts tours point at up to 10 parts, the people and things the explanation names first (each person by name). Named people are put on real faces (`FaceFinder`: Apple Vision on the close-up, on device; `FaceSnapping`): a part around a face moves onto one, each face used once, matched left to right — the model reads names well but places people loosely (it put two of three actors on one person). Which name is which face is still the model's call, so labels keep their "~". Inside a walkthrough, opening or switching apps is still green ("opening Safari…", "opened Safari"); only its final "done" tick is lavender. While it shows "checking…" it spins lavender where it points (`isTutorialChecking`). Planning a walkthrough spins lavender from the moment it's known to be one (asked outright, a how-to naming an app, or sorted as a walkthrough), not only once the steps are ready. Reduce Motion: thinking pulses instead of turning. **Look (2026-10-11, after Clicky, MIT):** a 16 pt triangle (was 15) built around its centroid (`EquilateralTriangle`: top vertex at midY − h/1.5, base at midY + h/3), so every rotation pivots on its dead centre; solid fill (was 0.9); corners rounded 1.5 pt (`EquilateralTriangle.cornerRadius`, scaled with the shape; Clicky's are sharp and only look soft through the glow; 2 pt looked small and blobby in a 2× render, user's request 2026-10-11) — a rounded 60° corner pulls the tip back by exactly its radius, so `tipDistance` is size/√3 − 1.5; resting angle −35° (was −45°); its centre 35 pt right and 25 pt below the hotspot (`OverlayController.triangleOffset`; at a screen edge it flips with the old 18/24 pt gap, `flipClearance`). The companion's glow (triangle and chat logo, `CompanionTriangle.glowOpacity/glowRadius`) is solid, radius 8 (was 0.6 / 4); the pulse still adds +0.4 opacity (capped at 1) and +4 pt. Measured with ImageRenderer at 2×: radius 8 is visible to 23.3 pt from the centre, 31.1 pt while pulsing (radius 12), 33.8 pt at radius 14; `drawingGroup` doesn't clip its own glow (100% kept at any angle), so the only clip is the panel edge — the companion canvas has a 16 pt margin above and left of the measured content (`CompanionBubbleView.canvasMargin`, triangle centre 35.6 pt from the panel corner). The listening waveform, pills and cards keep `Glow` (0.6, 4 pt), as do the capsules and the peel's small panels (they pass it to `CompanionTriangle`). Benchmark before → after (main thread / stalls, `CLICKBAIT_BENCH=1`): spin 0.37 → 0.36 s / 0 → 0; tour 1.21–1.29 → 1.23 s / 0 → 0; point 0.22–0.23 → 0.21 s / 0 → 0. **Follow (2026-10-11, after Clicky):** an underdamped spring, SwiftUI's `.spring(response: 0.2, dampingFraction: 0.6)` = `Spring(period: 0.2, damping: 0.6)` (`followSpring`, velocity carried in `followVelocity`), stepped in the display-link frame loop; it overshoots ~9.5% of its lag when the mouse stops and settles within ~0.6 s; Reduce Motion: critically damped (`calmFollowSpring`). Was an exponential ease (`followTime` 0.11 s). The trip home after pointing still glides on `glideSpring` with its speed (`returnVelocity`) and hands that speed to the follow within 4 pt. `Spring.step` is now the exact closed-form motion (under-, critically and over-damped): stepping in 1/240 s slices was up to 5% off for this stiff spring (overshoot 8.0% instead of 9.5%); any frame length now gives the same path. Benchmark: spin 0.36–0.37 s, tour 1.17–1.21 s, point 0.18–0.20 s, 0 stalls (no follow frames while the mouse is still). Benchmarked: no added stalls or main-thread time. Both are clock-driven (`TimelineView`, paused when idle). Typed messages set the thinking state too (they stayed idle blue).

#### The chat belongs to where it was summoned
The chat stays on the desktop and with the app it was summoned in (`ChatController` home app). While another app is in front it steps away (hidden, nothing lost) and it's back where it was when that app is (`NSWorkspace.didActivateApplicationNotification`). Summoning it again elsewhere (double tap ⌥⌘) re-homes it there. An answer that arrives while it's away shows two pills where the user is: "answer's ready in Safari" riding with the companion (fades after 5 s), and below where it appeared a stay-put [let's see!] [later.] pill (fades after 10 s; Esc = later). "let's see!" clears both pills and brings that app forward, where the chat is waiting; going back there yourself clears both. The "answer's ready" pill stays its full 10 s even when the user clicks in other apps (`OverlayController.showReadyNote`; a click took it away at once, 2026-10-12, and the answer seemed lost). Walkthroughs take it along when they open or switch apps (`adopt`), since the checklist lives in it. Coming back, it shows 0.35 s after the app activates; a full-screen app's slide can take longer (it landed on Chrome's desktop and Claude's had none), so for ~1.5 s after, each finished desktop switch (`activeSpaceDidChangeNotification`) and checks at ~0.8 s and ~1.5 s move it to the desktop in view if it isn't there (`isOnActiveSpace`, logged).

#### Pills before the chat
If a pill can say it, there's no chat. Pointing (blue pointer, labelled with the reply's own few words when they fit, `PillText`), an action's result (green), an error (black) and a short friendly answer (`PillText.fits`: one sentence, ≤32 characters — "Yep, it's on!") open no chat; the prompt asks for such replies when pointing or for simple facts. Longer answers, explanations, steps and code go to the chat; lavender walkthroughs always do. In a chat, such replies **park** it (`ChatController.park`: tucked, conversation kept; the "nothing in progress" safety net leaves it alone) until a long answer, a double tap ⌥⌘ or a new chat. A streaming answer brings the chat back only once it can't be a pill (a second sentence, or a first sentence past 32 characters). Near the right screen edge the chat's header flips (logo top-right) so the logo still sits on the companion. A double tap ⌥⌘ with text highlighted: the first tap's explanation may already have started its chat; it's only opened at commit and dropped on undo, so the double tap always gets a fresh (or the previous) chat.

#### Chat tucks away while the answer comes
Sending a message (spoken or typed) tucks the chat panel into the companion (`ChatController.tuck`: shrinks, hidden, keeps its place; a first question opens tucked). Only the panel steps aside — pills, pointing and the orange spin carry on. When it appears (`untuck`) it pops out of the companion wherever the companion is at that moment, then stays there (`homePoint`); returning to its app shows it where it was as soon as the answer's first full sentence is in (`SentenceSplitter`), or at once for a reply, error, "Stopped", a tutorial checklist or the final answer; and whenever ClickBait goes idle with nothing in progress, so it can't stay hidden. If the text field had the keyboard, it gets it back.

#### Type to ask (double-tap ⌥⌘, or ⌥⌘ + right-click)
Double-tapping ⌥⌘ (two taps within 0.3 s, `DoubleTapDetector`) opens the same chat without the mouse or a selection. A single tap still explains instantly (the request starts at once); for that 0.3 s it stays undoable: an open chat is detached but left on screen, and a "nothing highlighted" error waits. A second tap (or Esc) cancels the explanation quietly and puts the chat back (`undoExplain`); otherwise `commitExplain` closes the old chat. A snip or another shortcut resets the detector.
Right-clicking while holding ⌥⌘ opens an empty chat at the cursor with the text field focused (the panel takes the keyboard without activating ClickBait). The right-click (down and up) is taken by `InputInterceptor`'s event tap, so the app shows no context menu; the following ⌥⌘ release is ignored (not a tap/explain). The first typed message goes through `sendTyped` like any follow-up.

## Greeting on coming back

**Greeting on coming back (user's request, 2026-10-20).** The first wake or unlock of the day (after ≥ 30 min away, or at launch), or any return after ≥ 4 h away, types a short hello with a kaomoji into the companion's pill by the cursor (`Greeting`, Core, tested; `Greeter` watches sleep, screen sleep and lock, then wake, screen wake and unlock — a wake while locked waits for the unlock). Written lines per time of day (morning, afternoon, evening, late night), no model call, no name (user's call), not repeated until 8 others have shown. Typed at 35 characters a second, held 1.5–2.5 s, then gone (user's call: 5 s was too long); a click or Esc clears it; Reduce Motion shows it whole; Azure like other idle pills. Shown only when the companion is idle (`OverlayController.showGreeting` returns false when busy, and that return isn't counted as greeted). Menu Greetings turns it off (`settings.greetings`, on by default). Debug: `open --env CLICKBAIT_TEST_GREETING=1 …/ClickBait.app` shows one 2 s after launch.

#### Chat bubbles (added after M1)
Every answer or ⌥⌘ explanation opens a chat bubble (`ChatController`: borderless non-activating panel that can become key, so typing never activates ClickBait and the user's app stays frontmost). Pinned where it appeared, draggable, sized to its card, open until ✕/Escape. Memory (`Conversation` in Core) is scoped to the bubble, text only, first exchange + last 9 kept; each message gets a fresh screenshot; gone on close, never written to disk. Typed follow-ups get text replies; ⌃⌥ voice follow-ups go into the open chat and are spoken; ⌥⌘ explanations are text and replace the open bubble. **Look (2026-10-11): dark Aqua on glass** (`AquaChrome.swift`; colours from Clicky's dark palette, MIT): the heads-up blur stays (as see-through as before) with a graphite tint on top (#1A1C1E → #121414 at 34%) and 3% pinstripes (a tiled 1×3 px image), 14 pt corners, a 0.8 pt #373B39 border (#444947 with Increase Contrast), a 10% white top highlight, the window's own shadow. Header: a translucent gel bar with a curved 16%→3% sheen and a hairline; the close button is a small Aqua red gel whose ✕ shows on hover. Text #ECEEED / #ADB5B2 / #6B736F, links #7ABEFF. Input: a recessed capsule; send is a round Aqua blue gel when it can send, graphite (no glow) otherwise — buttons use Aqua's colours (blue #8CC8FF→#3D8EEA→#1B5FD1 rim #164FAF, red #FF8A80→#F2463E→#C7261F, green #5BD25B→#2E9E36, graphite #6B6F72→#3A3D40), never the companion's; pressed: the gloss dims and it moves down 1 pt. Code: a darker see-through well; "Copy" a graphite gel pill, "Copied" ✓ in Aqua green. The header's triangle keeps the companion's colours. Fixed-size chrome is cached (`drawingGroup`); the body and wells resize with streamed text and draw directly. Debug renders: `CLICKBAIT_RENDER_CHAT=<folder>`; streaming bench (no model): `CLICKBAIT_BENCH_CHAT=1` — main thread per 7.3 s of streaming, with a tour alongside: old look 1.47–1.59 s, new 1.65–1.67 s, 0 stalls.

The chat card grows out of the companion and shrinks back into it (`ChatModel.companionAnchor`: the companion's point inside the card, recomputed after the card is pushed on screen; scale 0.08 → 1 spring, 0.18 s ease-in back).

The overlay windows live on the current desktop only (`.moveToActiveSpace`, brought along on every desktop switch by `followSpaces`), are `.transient` (Mission Control hides them) and `sharingType = .none`: screen-sized and on all desktops at once, they turned every desktop thumbnail in Mission Control black — confirmed gone with ClickBait quit. Smoothness, measured (`sample` while moving the cursor, 2026-10-04): most busy main-thread time was moving the companion's window every frame (`NSWindow setFrame` → a synchronous window-server fence; slow whenever Ollama keeps the GPU busy) and fetching the cursor image to check for invisible cursors. Now the companion and the guide label each sit in a see-through, click-through window covering the whole screen (`StagePanel`) and move *inside* it (a Core Animation update; the window moves only when the content crosses to another screen), and the cursor image is fetched at most twice a second. A second sample showed the next costs: changing the menu-bar icon per state (each change waited on the window server: the icon now stays the same, only the menu's status line changes) and `Speaker.stop()` asking the synthesizer `isSpeaking` (~100 ms at every press of the talk keys: now only when ClickBait queued speech). The app under the cursor comes from the window list (normal windows, ClickBait's own excluded), since an AX hit test would now land on the overlay. Smoothness: at rest the frame loop runs at 30–60 Hz (10 Hz made the start of a movement steppy); the stall log ignores a hidden companion. The companion's frame loop runs on the main thread, so main-thread work stutters it. Streamed answers update the chat at most every 80 ms (they redrew and resized it per fragment), the chat window is resized only when its size really changes, and a gap over 80 ms while the companion moves is logged ("Companion stalled N ms (state)") to trace any stutter that's left. **Performance pass (2026-10-06)**, measured with Time Profiler, `sample` (blocked threads too), the stall log and Ollama's server log: idle CPU is 0.2–0.3% with the mouse still; 13–20% of a core while spinning, walking through or touring. The stalls aren't ClickBait computing: in 101 logged stalls (14.9 s) the main thread used 0.9 s of CPU; it was blocked in Core Animation commits waiting on the window server (87% of blocked time), and the ~85 ms tour stalls land at the same two points of every second even when ClickBait does nothing else, so part of it is the window server being busy. Tried and dropped (no gain measured): keeping the guide label's window ordered in and fading the label instead of the window. Benchmark: `CGWarpMouseCursorPosition` in a circle for 19 s while profiling (scripted, repeatable). Kept: the stage content no longer moves by `setFrameOrigin` (AppKit bookkeeping cost ~10× the move: frame-change notifications, focus/tracking-area updates, constraints) but by the stage layer's `sublayerTransform` (same fractional position, never animated) — main thread 1.36–2.01 s → 0.59–0.83 s per 19 s of motion, CA commit 524–647 → 74–109 ms, SwiftUI hosting layout 259–323 → ~0 ms. The microphone's next engine is prepared off the main thread after each release (`AudioRecorder.prepare`, 21–33 ms of main thread each time); the start at the press stays on the main thread (moving it would reorder what happens at the press), and still takes ~0.06 s. Debug builds launched with `CLICKBAIT_BENCH=1` (`open --env CLICKBAIT_BENCH=1 …/ClickBait.app`, mouse parked in a corner) play a fixed 6 s thinking spin, a 6-stop tour and one blue point, logging "Bench: …" per phase (`OverlayBenchmark.swift`) — the stalls reproduce there with Ollama idle. Their cause: while the triangle pulsed, its glow sat in a `.drawingGroup()` redrawn every frame (the glow changes each frame), and SwiftUI waits for the window server to show the previous frame before redrawing one (`RB::CommitMarker … waitForCommitId`, ~1.2 s of every 15 s). The drawing group is now used only while not pulsing (spinning keeps its turn-a-cached-texture saving; same pixels either way, checked with `ImageRenderer`; the swap has no transition): tour + point stalls 18 / 24 → 4 / 3 / 4, main thread 1.87–2.21 s → 1.01–1.68 s. Ollama runs one request at a time (`-np 1`), so a "parallel" request just queues; the first ~990 prompt tokens (instructions) are already reused from Ollama's cache, the screenshot costs ~2.4 s to encode. Code blocks wrap long lines (a sideways scroll view shifted wide lines left and cut both ends); Copy gives the exact code.


**Answers read in short paragraphs (2026-11-01, user's report: one big paragraph).** One formatter for the chat and the dock cards (`MessageFormat.attributedProse`): a paragraph over ~180 characters with three or more sentences shows as paragraphs of two sentences; a list written inline ("1. … 2. … 3. …") gets a line per item; markdown the inline renderer showed raw is tidied ("# Heading" → bold, "-"/"*" → •, nested → ◦, "---" dropped, a stray "**" removed, blank runs cut to one). Only how it's shown changes, never the words.
